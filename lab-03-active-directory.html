Lab 03 – Active Directory + AS-REP Roasting

Case Study: Domain Construction and Credential Exposure from a Weak Account Setting

July 2026 · Intermediate Identity Security

1. Context

Active Directory centralizes authentication and authorization for Windows environments. That convenience also creates concentrated risk. If account options are misconfigured, credential material can become easier to obtain.

This lab has two layers: first, building a functioning domain; second, demonstrating how one weak setting enables AS-REP Roasting.

Learning level: Intermediate
Focus: Domain services, Kerberos exposure, configuration risk

2. Core Concepts

  • Domain: a managed identity boundary, here named lab.local
  • Kerberos: the common authentication protocol in Active Directory
  • Pre-authentication: a control that helps prevent easy offline guessing of credentials
  • AS-REP Roasting: requesting authentication data for accounts that do not require pre-authentication
  • Password hash: a protected representation of a password that can be attacked offline if captured

3. Environment

  • Domain controller: DC01.lab.local
  • Domain: lab.local
  • Windows 11 client joined to the domain
  • Kali Linux as the attacker system

4. Procedure

Step 1 – Establish the domain controller

Windows Server was configured as the domain controller for lab.local. This created the central identity service used throughout the lab series.

Step 2 – Validate domain and network state

Before any attack simulation, domain membership and network settings were verified. A broken identity lab produces unreliable results.

Step 3 – Create identity objects

Users and group structure were created so the domain contained realistic objects for both administration and attack testing.

Users and groups inside the practice domain

Additional directory objects used in the lab

Step 4 – Introduce the weak setting

One account was configured without Kerberos pre-authentication. In practical terms, that account no longer required the normal initial proof step before authentication data could be requested.

Step 5 – Execute AS-REP Roasting

From Kali Linux, Impacket was used to request authentication material for the weak account. The result was a recoverable hash that could be attacked offline.

5. Analysis

This lab separates two important ideas:

  1. building a working identity environment
  2. understanding how a single control failure changes attacker opportunity

AS-REP Roasting is useful as a teaching case because the root cause is configuration, not exotic malware. The exposure begins with an account setting.

6. Conclusion

The domain was successfully built and the weak account setting produced recoverable authentication material.

Main takeaway: identity hardening is part of security operations. One overlooked account option can create credential exposure before broader compromise occurs.
